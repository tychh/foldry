# Цель

Общая цель - сделать мультиплатформенное приложение, которое позволяет выбрать каталог и упаковать его, не включая определенные вложенные файлы и папки.

Архитектурно приложение должно состоять из двух частей:

- ядро/бэкенд, написанное на Rust
- GUI на React + TypeScript

Для GUI можно использовать shadcn/ui или Mantine.

GUI: 
- отображает папки и правила
- позволяет редактировать профили с правилами и переключать их
- показывает preview (что будет упаковываться, а что нет в папке)
- позволяет запускать команды
- показывает прогресс и ошибки
- показывает результат выполнения

В GUI должна быть поддержка drag-n-drop (если нужная папка просто закидывается в интерфейс)

Rust бэкенд занимается:
- обходом файловой системы
- применением правил
- созданием архивов
- вычислениями (хеши и т.п.)
- отслеживание прогресса
- выполнение команд (actions)

Конфигурация хранится в YAML файле/файлах.

Как это все должно работать.

## Профили

В Gui должен быть режим редактирования профилей.

Должна быть папка `profiles/`, где складываются правила по которым игнорируются папки и файлы при упаковке. Каждый такой файл - это отдельный профиль упаковки, у него должно быть имя. Синтаксис файла - практичный subset от git.ignore (пример можно посмотреть в ignore.cfg). Но ты можешь расширить этот subset по необходимости. Расширение для файлов с профилями выбери сам так, чтобы оно было логичное и могло определяться/редактироваться нормальными редакторами, файловыми менеджерами и IDE, как понятный и редактируемый текстовой файл. Я выбрал изначально `.cfg`, но, возможно, ты придумаешь что-то лучше.

Через GUI должна быть возможность переключаться между профилями, создавать новые профили, редактировать профили, удалять профили. По умолчанию, должен быть профиль `Default` - его ты можешь взять сейчас как готовый набор правил из `ignore.cfg`

Каждый отдельный профиль можно редактировать руками как текст (должна быть подсветка синтаксиса), Кроме того, при редактировании должна быть возможность вставлять/удалять различные пресеты для конкретных языков/фреймворков/сред разработки. То есть должна быть возможность, например создать новый или открыть готовый профиль, кликнуть на пресет `Python` и в профиль вносится готовый блок того, что должно игнорироваться для Python.

Общий смысл всей системы, в том, чтобы при выполнении действий (сейчас это только упаковка) игнорировать runtime артифакты в репозиториях/папках. При этом секреты/настройки могут игнорироваться, а могут и нет. Поэтому пресеты должны быть заточены именно на это. Надо сразу сделать хороший набор готовых пресетов.

Так как пресет вставляется просто как текстовой блок внутрь профиля, он должен как-то помечаться, чтобы система знала, что это именно этот пресет. Если пресет уже вставлен, то второй раз он вставляться не должен. Если пресет в тексте изменен руками, то вставить его еще раз тоже нельзя, но можно удалить. 

Вероятно, сами пресеты нужно показывать в GUI как небольшие карточки: название, очень лаконичный комментарий, статус (вставлен/изменен).

Неизмененный пресет удаляется из профиля просто повторным нажатием на карточку пресета. Измененный пресет удаляется после подтверждения. Подтверждение запрашивать прямо в самой карточке (чтобы пользователь не искал по экрану).

Получается, что в режиме редактирования профилей должно быть:

- быстрое и простое переключение между профилями
- кнопка создать новый профиль
- кнопки сохранить и удалить профиль
- режим автосохранения профиля
- список с карточками пресетов, которые можно вставлять в профиль или удалять из профиля
- область просмотра и редактирования текущего профиля с простой подсветкой синтаксиса

Опцию включить/выключить автосохранение профилей нужно вынести в интерфейс режима редактирования профилей.

Как я вижу GUI в этом режиме:
- слева список профилей
- в центре область для редактирования профиля
- справа список пресетов


## Выбор рабочей папки

В основном режиме система должна показывать:

1. Область выбора папки/папок. Область должна показывать дерево папок с возможностью выбрать одну или несколько папок. Узлы дерева должны раскрываться/закрываться, чтобы не показывать лишний шум.

2. Область, где показываются карточки выбранных папок.

3. Кнопки "Выполнить" (выполняет действия для всех выбранных папок), "Очистить выбор" (очищает список выбранных папок).

4. Область "Выбрать output каталог по умолчанию", где показывается каталог по-умолчанию для результатов упаковки и где его можно задать (кнопка выбора). Этот каталог автосохраняется в настройках системы.

5. Кнопка настроек упаковки по-умолчанию: выбор формата архива и степени сжатия.

Для каждой выбранной в дереве папки создается карточка в списке выбранных папок.
Там показывается путь к папке, используемый профиль, действие, которое нужно выполнить, но сейчас там только "упаковка". Если действие "упаковка", то должен показываться результирующий каталог, куда должен быть положен архив (он берется по умолчанию для результатов упаковки, но должна быть кнопка, чтобы его сменить, если нужно) и кнопка настройки типа архива и сжатия (это по умолчанию берется из настроек системы, где должны быть эти опции, но должна быть возможность выбрать индивидуально для конкретной задачи).

При выборе карточки, появляется область с выбором настроек для этой папки: действие, профиль.

Выбор папок и настройки для каждой папки автосохраняется. При следующей загрузки системы, он должен оставаться.

Должна быть также возможность запустить настроенное действие для конкретной папки (а не для всех вместе). Для этого должна быть кнопка на самой карточке папки и кнопка в настройках папки.

Как я вижу GUI:

- Слева дерево папок
- В центре список с карточками выбранных папок
- Справа область настроек для выбранной папки
- Снизу область с общими настройками и кнопками и общим прогресс-баром (когда выполняется работа)

Выбор результирующей папки, настройки упаковки делаются в модалках.

На карточке есть значок показывающий результат выполнения: не выполнялось/успешно/ошибка. Если при выполнении задачи для папки произошла ошибка или завершено успешно, на значок можно нажать и посмотреть лог по задаче.
Для каждой карточки тоже показывается отдельный прогресс-бар. 

После запуска задачи для папки, на карточке должны активироваться кнопки пауза и стоп, чтобы можно было приостановить или отменить задачу. Если задача на паузе - новый поток выполнения не запускается, удерживается задачей. Если задача остановлена, поток освобождается и может выполнять следующую задачу.

Пауза реализуется как "мягкая" - завершается обработка текущего файла, задача не уничтожается, но новые файлы не читаются и освобождается CPU, слот параллельности формально остается занятым.

Кроме того, должны быть глобальные кнопки "Поставить все на паузу" и "Остановить все".

Еще нужна настройка: сколько одновременно задач обрабатываются. Задачи обрабатываются по очереди. Количество параллельно выполняемых задач настраивается пользователем.
Остальные задачи остаются в очереди.

Нужно сделать настройку как решать конфликт, если архив есть - перезаписывать, ничего не делать, инкрементировать имя.

Интерфейс сразу предполагаем мультиязычный, но только для GUI. CLI - английский.

События прогресса throttled до 10 обновлений интерфейса в секунду.
Команды, изменения состояния и ошибки отправляются немедленно. Логи читаются по запросу.

Должна быть возможность добавить папку через drag-n-drop.

Используем светлую и темную темы.

В дальнейшем мы будем развивать приложение: будут добавляться другие действия, которые можно делать с папками, применяя фильтры-профили. Например - передать на сервер через ssh, синхронизировать, отправить архив и т.п. И возможно, добавятся сценарии, чтобы можно было комбинировать или выполнять сразу несколько действий или цепочку действий.

Также должна быть возможность работать через командную строку.

Видимо, также нужно сделать какой-то синтаксис для списка задач (он же список папок+действие), поскольку этот список должен быть в виде текстового файла, расширение придумай сам.

## История и runtime-состояние

Их можно хранить в SQLite, где-то в state/app.db

У профиля должен быть стабильный идентификатор. 

У пресетов можно сделать четыре состояния: absent/installed/modified/outdated. Для каждого пресета можно считать hash после нормализации (в тексте) и сравнивать с hash пресета.

Можно сделать редактор пресетов, так, чтобы их тоже можно было редактировать и сохранять с уникальным именем (и id если нужно).

Вероятно, стоит разделить пресеты на безопасные и чувствительные.

В безопасные попадут, скорее всего:

Python;
Node.js;
Rust;
Go;
Java/Gradle/Maven;
.NET;
PHP/Composer;
Ruby;
C/C++;
CMake;
Django;
React/Vite;
Next.js;
Vue;
JetBrains;
VS Code;
macOS;
Windows;
Linux;
test caches;
coverage artifacts;
build output.

В потенциально чувствительные можно:

environment and secrets;
local configuration;
certificates and keys;
database dumps;
private media;
deployment credentials.

Для чувствительных можно выдавать предупреждение (на самой карточке пресета или при вставке).

Правила фильтрации применяются последовательно, последнее совпавшее определяет результат.

Для preview результата фильтрации нужно показывать и результат и причину (то есть при наведении например показывать какое именно правило сработало, строка такая-то в профиле, если есть то и какой пресет)

И да, я тут везде говорил "карточки выбранных папок", но по факту мы пришли к тому, что каждая карточка - это задача. Так что пусть это будут карточки задач.

Дерево файловой системы подгружается лениво. Для Linux показываются как недоступные /proc, /sys, /dev, каталоги без прав на чтение. Сетевые mount points и symlinks надо как-то выделять цветом.

Drag-n-drop брошенная папка создает новую задачу (а несколько - несколько задач). Брошенный файл - игнорируется. Дубликат игнорируется.

Scheduler/executor должен резервировать output path перед началом записи.

Архив лучше сначала создавать во временном файле

При overwrite нельзя сначала уничтожать рабочий архив, а затем надеяться успешно создать новый. Нужна безопасная замена через временный файл.

Политика обработки:
обычные файлы            → включать
директории               → обходить
symbolic links           → сохранять как ссылки, не следовать
junctions                → не следовать
special files            → пропускать с warning
unreadable files         → fail task или warning по настройке

Форматы архивов:
ZIP
TAR.GZ
TAR.ZST
но список будет пополняться

Compression level лучше нормализовать на уровне UI: 
Fast
Balanced
Maximum

Одна карточка задачи может иметь много запусков. Надо как-то вести журнал/лог.

По клику на статус показывать:
